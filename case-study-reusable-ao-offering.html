Deliverable 2 · Lifecycle integration

One coherent offering: Design → Deploy → Operate → Assure → Improve

AO is not a tool drop — it is a services product that wraps the closed loop. Intent & policy set the “what good looks like”; AI / orchestration / assurance execute and prove it.

01
Design

Intent, KPI contract, domain model, reuse catalog selection

02
Deploy

Onboarding, SPOG/connectors, shadow→live, change governance

03
Operate

L1–L3 model, auto-actions, A-team for leakage (P1)

04
Assure

SLA/OKR scorecards, audit of auto-actions, trust gates

05
Improve

Top-offender → RC → sunset workarounds → next autonomy level

Where AI plugs in

  • Anomaly / log mining for Predict
  • Self-healing playbooks for known failure classes
  • GenAI SOPs / knowledge (H3G: KT → usable repo)
  • Localized models per region/account (reuse + adapt)

Orchestration & assurance

  • Workflow: detect → classify → act → verify
  • Ticket/ITSM + monitoring bus (SPOG pattern)
  • Assurance: did auto-action improve the KPI?
  • Human-in-loop for high-risk classes

Intent-based & policy-driven

  • Intent: “Keep voice/data NPS, cut P1s, hold margin”
  • Policy: thresholds, auto-approve vs escalate
  • Guardrails for sales/delivery (what’s in package)
  • Regional policy packs without forking the product

Lived parallel (H3G UK): Observe (Dynatrace/Splunk → Grafana SPOG) → Categorize (top offenders) → Contain (governed workarounds) → Autonomize (self-healing) → Improve (RC + sunset). Same loop, productized as an offering with KPI gates.

Deliverable 3 · Observability & data foundation

Measure outcomes · then let KPIs drive the roadmap

Customer-agreed KPIs/OKRs are the commercial spine of the offering. If we cannot observe it, we cannot sell autonomy — or prioritize investment.

Data foundation (minimum viable)

  • Telemetry: metrics, logs, traces (existing + gaps)
  • Topology / CMDB: app & infra ownership map
  • Incident history: 6–12 months for baseline & offenders
  • Business lens: domain alerts (not only infra noise)
  • SPOG: one pane for 24×7 SDM / ops leadership

Deliverable 4 · Architecture for reuse

Productized capability · not a bespoke project

Leadership expects reuse across customers. Architecture separates a shared AO platform core from customer configuration (intent, policies, connectors, localized models).

Reusable core (product)

  • Autonomy maturity framework & phase gates
  • SPOG / alert correlation patterns
  • Top-offender engine & taxonomy
  • Self-heal playbook library (versioned)
  • KPI scorecard & OKR review cadence
  • GTM pack: tiers, guardrails, enablement

Customer config (not fork)

  • Intent & policy thresholds
  • Domain/vendor connectors
  • Localized LLM/use-case packs
  • Org model (L1–L3, A-team)
  • Commercial tier & SLA band

Trade-offs (be explicit)

  • Speed vs reuse: more config up front, faster Nth customer
  • Depth vs standard: deep custom = margin risk
  • Auto vs trust: start with human-in-loop
  • Global vs local: policy packs, not code forks
  • Tool lock-in: abstract SPOG; keep adapters thin
